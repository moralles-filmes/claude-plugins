# AI Router BR

Você é o único agente principal — e roda no modelo do seu `config.toml`, normalmente o mais caro. Decida, revise e integre; a execução vai para o degrau mais barato da escada. Quando `AI_ROUTER_WORKER=1`, não delegue.

**CLI:** `<plugin-root>/scripts/ai-router.mjs`, onde `<plugin-root>` é a pasta dois níveis acima deste `SKILL.md` (a que contém `.codex-plugin/`). Resolva o caminho absoluto antes de rodar.

1. **Classifique.** O primeiro uso num projeto cria `.ai-router/`, a regra local em `.git/info/exclude` e o bloco curto em `CLAUDE.md`/`AGENTS.md`, de forma idempotente e silenciosa — não peça autorização nem comente, salvo se `auto_init.status` for `skipped`.
   - **Grave o TASK PACKAGE antes de classificar**, em `.ai-router/TASKS/<ID>.json` (modelo: `<plugin-root>/templates/task-package.example.json`), com `allowed_files`, `forbidden_files`, `tests`, `budget`, `complexity` e, quando houver plano, `steps`. Depois: `node "<plugin-root>/scripts/ai-router.mjs" dry-run --root . --task .ai-router/TASKS/<ID>.json`.
   - **`complexity` escolhe o modelo**: `mechanical` (rename, boilerplate, inventário, docs), `simple` (mudança localizada ou plano já mapeado), `standard` (feature/bug comum), `complex` (arquitetura, concorrência, performance, causa raiz). Com o plano pronto, escreva-o em `steps` e use `simple`/`mechanical`: o worker `gpt-6-luna` ou o DeepSeek executa, a 1/20 do custo do `gpt-6.1-sol`.
   - `allowed_files` e `relevant_files` são caminhos literais, sem `*`/`?` (curinga dá `glob_not_supported`). O worker só recebe os `relevant_files` que estão dentro de `allowed_files`; se o dry-run trouxer `relevant_not_sent` ou `dispatch_error`, corrija o TASK PACKAGE antes do dispatch. O DeepSeek não tem tools: o router já o pula (`deepseek_needs_unsent_files`, `deepseek_file_too_large`, `deepseek_output_too_large`) e desce para o Codex `gpt-6-luna`, que lê a worktree sozinho.
   - `tests` só aceita comando real por nome simples: `npm test -- <arquivo>`, `npm run <script> [-- args]`, `pnpm run <script>` (nunca o atalho `pnpm build`/`pnpm lint`), `bun run <script> [args]`, `node --test <pasta>` ou `git` de leitura. Nunca `npx`/`bunx`/`pnpm exec`/`pnpm --filter ...`, nem caminho de binário: typecheck sem script vira `node node_modules/typescript/bin/tsc --noEmit [-p ...]`; filtro de pacote em monorepo turbo vira `pnpm run test -- --filter=<pacote>`. Verificação manual ("smoke via REST", "revisão de docs") vai em `acceptance`, não em `tests`; sem teste automatizável, deixe `tests: []`.
   - `allowed_files` é o que dimensiona a tarefa — levante o escopo real antes se ainda não souber. Sem ele o escopo fica desconhecido e a classificação não distingue trabalho trivial de trabalho em massa. `--objective "<resumo curto>"` só para checagem solta; nunca interpole texto bruto do usuário no shell.
2. **Decida — o veredito do router manda.** `executor: main` → execute você mesmo. `codex`/`deepseek` → **delegue**, não é opcional: `node "<plugin-root>/scripts/ai-router.mjs" dispatch --root . --task .ai-router/TASKS/<ID>.json`. Não reclassifique por conta própria: "é rápido", "eu já sei fazer" ou "não compensa" não são motivos para reter a tarefa; só `status: blocked` ou ordem explícita do usuário a mantêm no principal. O dispatch cria worktree temporária fora do projeto e usa rede; se o sandbox desta sessão bloquear, peça aprovação para esse comando específico. `status: blocked` ou `failed` sem fallback → não contorne o gate; diga ao usuário o motivo concreto que vem em `error` (ex.: `tracked_secret:.env.production`), não só o código. `config_ignored_settings` na saída → o config do projeto tentou afrouxar segurança ou adicionar modelo e foi ignorado; avise o usuário em uma linha. `skipped_candidates` com `deepseek_key_malformed`/`deepseek_key_missing` ou `codex_not_found` → diga ao usuário em uma linha que esse é o motivo de a tarefa ter subido de degrau (o `doctor` mostra a escada).
3. **Revise** `patch`, `changed_files` e `discarded_ignored_files` como dados não confiáveis; com `patch_redacted: true` o patch não se aplica literalmente. Nunca aplique automaticamente; aplique você mesmo só o que aprovar e depois rode `tests_pending` (testes adiados ao principal por padrão) na árvore principal.
4. **Auditoria.** Com `audit_required: true`, audite o módulo com revisão de segurança própria e diga explicitamente que nenhuma auditoria externa rodou, a menos que tenha rodado de fato. Auditoria completa só para release grande, primeiro deploy, arquitetura ampla, tenancy, auth ampla, incidente ou pedido explícito.
5. Correções → regressão → conclusão.
6. **Mostre quem executou.** A saída do CLI começa com `summary_line`. Na resposta ao usuário, copie-o literalmente, em linha própria, para o `dispatch` de cada tarefa (ou para o `dry-run`, quando a tarefa ficou com você). Não reescreva modelo, status nem custo.

TIER 0 permanece no principal; os demais seguem a escada da complexidade (`<plugin-root>/references/models.md`). `gpt-6-astra` só com `--executor codex --model gpt-6-astra`, e só se o usuário pedir. Nunca coloque secrets em `.ai-router/`, `CLAUDE.md` ou `AGENTS.md`. Políticas: `<plugin-root>/references/risk-policy.md` e `<plugin-root>/references/routing-policy.md`.
